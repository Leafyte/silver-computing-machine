# India ETA acting and approval controller

**Status:** implemented as a local prototype on 2026-10-29. Workflow examples are synthetic fixtures. The controller does not assert that it has live fleet state, calibrated Indian ETA uncertainty, or a production authorization system.

## Interfaces

`EtaController(db_path, *, clock=None, optimizer=None, evaluator=None, projector=None)` uses a persistent SQLite database. The injected callables are intended for deterministic unit checks; the default path uses the local India ETA optimizer and state projector.

- `register_plan(payload, actor) -> dict` creates and activates version 1 after it recomputes the validator result and joint-scenario cost from the supplied scenario and plan. `payload` requires `plan_id`, `version=1`, `model_version`, timezone-aware `as_of`, `scenario`, `weighted_scenarios`, and `plan`. Optional fields are `currency`, `operating_rate`, `switching_cost_threshold`, `switching_cost`, `cooldown_seconds`, `expiry_seconds`, `hysteresis_cost_threshold`, `mode`, and supplied `validation`/`expected_cost` for equality checking. `eta_model_identity` is optional and server-only: exact object `{model_id,model_version,model_sha256}`, with matching `model_version` and lowercase 64-character SHA-256. The API adapter must derive it from trusted configuration, never forward a client value. It is persisted across approved versions; pre-identity databases remain null. Defaults are `XTS`, 1.0, 0, 0, 120 seconds, 900 seconds, 5 XTS, and synthetic scenario mode. Only a server-resolved `dispatcher` or `admin` actor can register. Live activation returns `unsupported_capability` until a verified live-state adapter exists.
- `process_event(payload, *, cancel_check=None) -> dict` requires `event_id`, `plan_id`, `plan_version`, `model_version`, timezone-aware `as_of`, `observed_state`, `scenario`, `weighted_scenarios`, and `event_type`. Each state row is `{vehicle_id, position, position_type, elapsed_minutes, available_at, completed_prefix:[{order_id,completed_at}]}`. Event types are `eta_update`, `delay`, `vehicle_status`, and `route_change`. State positions must be explicitly simulated today; every weighted scenario is a complete travel matrix labeled with `source_label` and `prediction_target: travel_time`.
- `approve_proposal(proposal_id, payload, actor) -> dict` requires `base_version`, `event_id`, `model_version`, and the internally generated `context_hash`. It rechecks proposal status and expiry, active version, event and async-job status, model/context hashes, independent feasibility, state-aware prefix constraints, scenario costs, hard-window outcomes, and recomputed net benefit inside one `BEGIN IMMEDIATE` transaction.
- `get_proposal(id)`, `get_manifest(vehicle_id, version=None)`, `get_active(plan_id)`, and `cancel_event(event_id)` provide durable reads/cancellation. Manifest `version` is a vehicle-scoped history sequence; `plan_version` records its parent plan version.

Actors can be a trusted role string or `{subject,role}` supplied by the backend auth dependency. The controller never reads a role from a request payload. The API layer owns credential validation and must pass only the resolved role/identity.

## Decision flow

Registration freezes a validated initial plan as active. An event first reserves its unique ID and ordered `as_of` context, then calculates the current plan from explicit vehicle positions and clocks. The controller compares that cost with the previous event context before invoking route optimization. A material change goes to the optimizer with both the immutable completed prefix and current vehicle state. The optimizer output is separately projected from each vehicle's supplied location and availability time, not replayed from the depot.

`KEEP` reports no material actionable change. `ALERT` reports risk or a failure to establish a beneficial valid alternative. `PROPOSE_REPLAN` stores an immutable pending candidate; it does not modify the active plan. Example from `fixtures/india_eta/workflow-propose.json`: under its synthetic matrices the current expected remaining cost is 64 XTS and the candidate is 37 XTS, so the measured fixture saving is 27 XTS. With explicit switching cost 30 XTS, net benefit would be -3 XTS and no proposal would qualify. This is arithmetic on synthetic matrices, not measured fleet performance.

Approval serializes concurrent requests, recomputes both current and candidate remaining costs using the same stored event scenarios, and subtracts the configured switching cost again. It does not trust a stored proposal benefit or projected manifest. It refuses a candidate that reassigns or changes a completed prefix, violates a hard window in any supplied scenario, falls below the configured minimum benefit, has expired, was cancelled, or has been superseded. Successful approval atomically inserts the next active plan version, audit entry, and vehicle manifests. Historical manifests remain queryable; vehicles removed from the new plan receive a versioned empty/revoked manifest.

SQLite tables are namespaced as `eta_plans`, `eta_events`, `eta_proposals`, `eta_manifests`, and `eta_audit`. Event body hashes enforce exact duplicate idempotency and reject reuse of an ID with changed content. A newer event supersedes older pending proposals. The observed completed-stop IDs, completion timestamps, and vehicle clocks cannot move backwards. `cancel_event` invalidates any pending proposal; `cancel_check` is also checked before and inside the proposal write transaction.

Cooldown seconds, minimum net benefit, and reverse-plan hysteresis are persisted with each plan version. A proposal that returns to the immediately previous route assignment must exceed `switching_cost_threshold + hysteresis_cost_threshold`. A configured ETA async job, when present, must already be `succeeded` before the proposal can be approved; queued, running, cancelled, failed, and timed-out jobs are rejected.

## Limits

This controller does not load or train ETA models, fit uncertainty, authenticate the event's simulated observations, execute a driver dispatch, or use a QPU. The `actual` state type is rejected because no verified live-state adapter is configured. A timeout/cancel callback suppresses proposal persistence; the surrounding API job adapter must persist its terminal status and invoke `cancel_event` when cancellation wins. No live API route integration or production authorization claim is made by this document.
